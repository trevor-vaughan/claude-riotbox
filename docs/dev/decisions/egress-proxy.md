# How should a session's egress be confined?

**Decision:** A per-session Envoy, digest-pinned, as the agent's only route
out: the agent on a podman `--internal` network, Envoy on that and a
DNS-enabled bridge, both in a `--infra=false` pod for lifecycle. A hostname
allowlist enforced on CONNECT without decrypting, changeable while the
session runs. Opt-in (`RIOTBOX_EGRESS=1`), podman only. Credential injection
is a separate, later decision.

**Date:** 2026-10-23 · **Branch:** `8-envoy-egress` · **Issue:** #8

> **Frozen design record.** For how egress works today, read
> [egress.md](../egress.md) and
> [README § Egress proxy](../../../README.md#egress-proxy).

## The problem

Issue #8 asked for an Envoy sidecar as the session's only egress path, with
credential injection and egress policy moved out of the agent container. A
session otherwise has the network access of any rootless podman container,
so an agent can send the project anywhere. The issue was split in two:
**A**, enforced egress (this record), and **B**, credential injection, to be
designed on its own. A must not preclude B: Envoy is in the path and its
configuration is generated by Go. B landed on its own branch on
2026-10-26; see [Credential injection (B)](#credential-injection-b-2026-10-26)
below.

## What we chose, and what we turned down

| Question | Chosen | Turned down, and why |
|---|---|---|
| Proxy | Envoy, the upstream distroless image pinned by digest | paude-proxy, the issue's first plan. Baking Envoy into the agent image (the gateway would carry the toolchain and `sudo`). A custom wrapper image (nothing to add). |
| Enforcement | agent on an internal network only | A shared-network-namespace pod, the issue's first idea: every member has Envoy's routes, so `HTTPS_PROXY` is only a hint. |
| Grouping | podman pod, `--infra=false`; docker refused in egress mode | Plain containers grouped by label: docker-compatible, but more teardown code. |
| Policy | built-in registries + the active agent's hosts + system and user `egress.conf`, with a live session overlay on top | Deny-all with config only (sessions break until configured). Allow-all with logging (no protection). |
| Live updates | allowlist in RDS, file-watched | LDS: a listener change drains open tunnels. Restarting Envoy: drops every connection. |
| Gate on `RIOTBOX_EXTRA_ARGS` | refuse flags that grant capabilities or networks, and mounts that could carry a host engine socket | Refusing every mount. Documenting the risk only. |
| Credentials | out of scope (sub-project B) | Doing both at once: injection needs TLS termination or `http://` base URLs, a separate architectural choice. |

## Evidence

Spikes on podman 6.1.0 rootless (netavark, pasta) and Envoy 1.40.1, run while
designing; their scripts were not kept:

- Internal network: no route out, container-name DNS only.
- A process with `CAP_NET_ADMIN` on the internal network added a default route
  via its gateway and reached the internet. Without it (the normal and
  nested-mode capability sets, as root via `sudo`): `RTNETLINK ... Operation
  not permitted`. The boundary is the agent's capability set, not the network.
- A shared-network-namespace pod did not confine the agent.
- Envoy on the default `podman` network could not resolve upstreams
  (`503`, flag `DF`): that network has DNS disabled. A DNS-enabled bridge fixed
  it.
- CONNECT allowlisting with `connect_matcher` and the dynamic forward proxy:
  listed host 200, unlisted 403, plain HTTP 403, wildcard matched.
- A listener (LDS) change drains open tunnels; a route (RDS) change does not.
- `envoy --mode validate` ignores dynamic resources, so validation needs a
  static rendering.
- `podman logs` returned nothing in the dev container (journald driver), so
  readiness reads Envoy's `--log-path` file instead.

**Amended 2026-10-24 (final review):** the internal network's
container-name DNS is gone. Older aardvark-dns and CNI setups may forward an
internal network's queries upstream, a DNS channel past Envoy, so
`<name>-int` is created with `--disable-dns`, the agent runs with
`--dns none`, and it reaches Envoy through `--add-host <name>-egress:<ip>`
with the address read from `podman container inspect`. Checked on podman
6.1.0: with DNS disabled the internal network gets no gateway address, the
agent would otherwise inherit the host's (unreachable) nameservers, and
Envoy's `resolv.conf` lists only the external network's aardvark-dns. A
fixed `--ip` was turned down: choosing one safely needs the subnet podman
picks, which can differ per session.

What is now proven by committed tests rather than by the spikes: the
`EPERM` as root and with nested flags, with a `NET_ADMIN` positive control;
the agent having no resolver and no answer from any nameserver it could try;
allowed/denied/plain-HTTP; live allow and deny with a tunnel opened before
them staying up; `envoy --mode validate` on the static rendering; teardown
and the orphan sweep (`task test:egress-e2e`).

Not verified: the choice of Envoy over paude-proxy rested on project health
(CNCF, active, regular releases) against a small project, not on a
comparative test.

## Amendments while the branch was open

Review on 2026-10-24 found that a bind-mounted host engine socket works across network
isolation, so the gate also refuses `RIOTBOX_EXTRA_ARGS` mounts whose source
is a Unix socket or is, lies under, or is an ancestor of the user runtime dir,
along with `--volumes-from`. Later review rounds added `--rootfs`, `--mount`
with `volume-opt=` or `type=glob`, and quoted `--mount` values. Accepted limits: a mounted directory
elsewhere that contains a socket, and a named volume created earlier with a
bind option.

On 2026-10-24, before the branch merged, `egress.conf` gained sections, a
`strict` setting and named host groups, so the format ships once. Strict
mode exists because some users want nothing implicit, not even the
registries or the agent's API; groups replace the template's copy-paste
host lists with names whose vendor sources are cited in
`internal/egress/policy/groups.go`. Overlay lines apply in file order, so
the latest `allow` or `deny` wins even when a group and one of its hosts
disagree.

Denials are explained in the agent's system prompt, not only in the 403
body, because clients drop the body of a refused CONNECT: curl reports
`CONNECT tunnel failed, response 403` and nothing more. The body and the
`x-riotbox-egress` header stay for clients that do show them, and a
non-CONNECT 403 says plain HTTP is never proxied, since telling the agent
to ask for the host there would not help. The body echoes the authority
the agent asked for, so it asks the user to check the host before allowing
it.

Pi's and opencode's `AGENTS.md` are shared by every session of a project,
and the user runs sessions concurrently; each launch's sync replaces the
file and opencode re-reads it on every model call. So their section is
static text keyed on `$RIOTBOX_EGRESS_SESSION`, installed at every start
and never stripped: a per-session section would name the wrong session,
and stripping it at a normal start would take it from an egress session
running beside it. Claude's managed `CLAUDE.md` is fresh per container and
keeps the section with the session name filled in.

Turned down: refusing a strict launch that leaves out the agent's hosts (a
warning instead: the user may mean it), user groups that nest (only
built-ins do), and expanding a live `allow @g` into hosts (the overlay
keeps the reference so a reload re-resolves it).

## Credential injection (B), 2026-10-26

**Branch:** `8-credential-injection`, stacked on `8-envoy-egress`. For how it
works, read [egress.md § Credential injection](../egress.md#credential-injection).

**Interception, not base URLs.** Pointing each agent at a plaintext base
URL on the proxy would need every agent to honour one per provider
(opencode ignores `ANTHROPIC_BASE_URL` and `OPENAI_BASE_URL`, per
`agents/opencode/headroom-exec.sh`) and would send keys in cleartext inside
the pod. Terminating TLS in Envoy for the credential hosts alone works for
any client that uses the proxy and takes an extra CA through an
environment variable, which every runtime in the image does. The CA is per
session, name-constrained to those hosts, and its key is never written.

**`credential_injector`, not `request_headers_to_add`.** Envoy 1.40.1 ships
the filter and its generic credential, which reads the key from an SDS
file. Keys then live only in the 0600 files of a secrets dir only the
proxy mounts, never in `rds.json` or any config the CLI prints. The route
pins the upstream `Host` to the provider, so a key cannot be fronted to
another domain behind the same CDN.

**30-day certificates.** The CA key is discarded at launch, so no leaf can
be renewed while a session runs; a short lifetime would cut a long session
off its provider. The spec's first draft said 24 hours; that was changed while
planning, as a shorter life buys little: nobody can sign with the CA after launch and
its name constraints bind it to the credential hosts, while the leaves'
keys sit only in the proxy's secrets dir, deleted at teardown. So CA and
leaves are valid 30 days, backdated 5 minutes for clock skew; a session
older than that needs a restart.

**Secrets on the runtime tmpfs, not in the data dir (2026-10-26, after the
branch review).** In the state dir the keys reached persistent disk, and a
broad project mount (`riotbox ~`) holding the data dir could expose them.
`$XDG_RUNTIME_DIR` (else `/run/user/<uid>`) is tmpfs, private to the user,
and already refused as an agent mount, so the secrets dir moved there. Only
a 0700 directory the user owns on tmpfs qualifies; with keys to inject and
none, the launch fails rather than fall back to disk or silently pass the
keys through. No setting chooses the location. The CA certificate and the
injection record, which hold no secret, stay in the state dir. The same
review added: no core dumps for Envoy, the orphan sweep run without the
forwarded variables, and the refusal of a shared PID namespace while keys
are injected (`launch.sh` keeps them in its environment). The older
exposure of `config/rds.json` to a broad project mount is left as a
documented residual and a follow-up.

**The outer listener stays HTTP/1 only.** Interception happens behind the
CONNECT, on internal listeners, so the reason for HTTP/1 there (the
denial text's authority) is untouched. Inside the decrypted tunnel the
client may negotiate h2 or HTTP/1.1.

**OAuth logins deferred.** Claude Code's `.credentials.json` and opencode's
and Pi's `auth.json` hold tokens the agent refreshes and writes back;
taking them out of the container needs a token broker, a separate design.

**`RIOTBOX_EXTRA_ARGS` that set an injected key are refused.** An
`-e NAME=…`, `--env-file` or `type=env` `--secret` would replace the
placeholder with a value of the user's choosing, the key included. Unlike
A's gate this check runs after `egress-up`, because only then is it known
which keys are injected; the EXIT trap removes the pod.

**Rows left out.** `ANTHROPIC_AUTH_TOKEN`: `api.anthropic.com` refuses a
bearer API key and Claude Code reports "Not logged in" with it alone, so
it serves gateways, which a base URL points at. `GOOGLE_GENERATIVE_AI_API_KEY`:
no agent's `env_vars` passes it.

## OS package mirrors, 2026-10-27

`sudo dnf install` failed in every egress session even with `@centos`
allowed. The image's repos use metalinks; `mirrors.centos.org` (allowed)
answered with ~27 third-party mirrors chosen by location, none in the
group, and `mirror.stream.centos.org` appeared only as `http://`, which
the proxy never forwards. EPEL's metalink behaves the same way.

**Chosen:** in an egress session, rewrite the distro's repos to its own
HTTPS mirrors, which its group lists. Each distro is a plugin, `os/<ID>/`
(CentOS, RHEL, Fedora, Debian, Ubuntu, Arch), holding its hosts and its
rewrite together, discovered like `agents/`. `riotbox-core` snapshots the
groups as `os.conf` at `egress-up`, as it does `agent.conf`, rather than
take a new option on every command.

**Turned down:** listing the third-party mirrors (they vary by location and
over time, and number ~30 unvetted hosts per distro); documentation only
(`@centos` stays useless); proxying plain HTTP for the OS hosts (reverses
the rule that plain HTTP is never forwarded); and, for Debian and Ubuntu
images without `ca-certificates`, turning off apt's TLS verification for
their hosts. apt's signed `InRelease` would still protect integrity, but the
rewrite refuses instead: a Debian-based dev image ships `ca-certificates`.

**Cost:** dnf no longer checks `repomd.xml` against the metalink's checksum;
TLS to the project's own mirror and GPG-checked packages stand in.

`@forges` was added at the same time: one name for git over HTTPS to the
common forges, opt-in and not part of `@registries`.
